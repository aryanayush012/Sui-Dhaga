# Jira-style UI Rework Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Rework Sui-Dhaga's screens into a clean Jira-style board, list and ticket. That means one status field (with Unstarted, Delivered and Rejected, and no On hold), inline editing, Total/Paid money fields, auto-opening WhatsApp, and staff management merged into Settings.

**Architecture:** One new migration adds the Unstarted stage, removes `on_hold`, and adds two RPCs: `set_status` (one entry point for every status change) and `set_paid` (writes a payment delta). Pure display logic lives in `src/lib` with unit tests. Screens are rewritten in place from small components (`StatusMenu`, `InlineField`, `Sheet`, `Lozenge`, `Avatar`). The security model, `board_orders`, `get_tracking` and the offline cache are unchanged.

**Tech Stack:** Next.js 15, React 19, TypeScript, Tailwind 4, Supabase (hosted dev project), Vitest, Playwright.

**Spec:** `docs/superpowers/specs/2026-11-20-jira-ui-design.md` (builds on `docs/superpowers/specs/2026-11-19-sui-dhaga-design.md`)

## Global Constraints

- Environment:
  - Vitest only starts from **PowerShell** (`Set-Location C:\Sui-Dhaga`). `npm run test:db` runs files sequentially against the hosted DEV DB, and a single "fetch failed" is a network flake, so re-run that file once.
  - `npm run db:reset` resets the dev DB and is guarded by `SUPABASE_DEV_HOST`.
  - Never print `.env.local` values.
- Security model unchanged:
  - RLS on every table.
  - Mutations only through `security definer` RPCs with `set search_path = public`; EXECUTE revoked from `public, anon` and granted to `authenticated`.
  - Errors are `raise exception '<code>'`.
  - Employees never see customer mobile, money edits, history or WhatsApp.
- Statuses: stages are `Unstarted, Cutting, Stitching, Ironing, Ready` (positions 1–5; the highest position is Ready). The end states are `special_state` = `delivered` | `cancelled`, and **`cancelled` is labelled "Rejected" / "अस्वीकृत"**. `on_hold` no longer exists.
- Money: whole rupees (integers). Payments stay append-only.
- Lessons from v1 reviews (binding):
  - WhatsApp opens **inside the tap**, either synchronously or with a pre-opened window. Never call `window.open` after an `await`.
  - `supabase.rpc(...)` must be awaited or `.then`-ed, never `void`-ed.
  - Use functional state updates for async writes.
  - Disable buttons while a request is in flight.
  - Use `uid()` (not `crypto.randomUUID`) and `siteUrl()` (`src/lib/site.ts`).
  - Photo URLs are signed with the user's client.
- UI: Hindi + English (`hi` `satisfies` `en` keys); touch targets ≥ 44 px; 360 px width; Jira look (blue `#0052CC` accent, grey `#F4F5F7` columns, status lozenges: Unstarted grey, Cutting–Ironing blue, Ready green, Delivered green outline, Rejected red).
- Commit messages end with a blank line and `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

1. **Owner picks "Ready" in the status menu on a phone:** WhatsApp must actually open with the ready message. The window opens inside the click, before the save. → Task 2 `statusEffects` unit tests decide when to open; Task 5 wires it inside the click.
2. **Karigar opens a Delivered or Rejected order found through search:** the ticket is read-only, and `set_status` refuses with `order_closed`. → Task 1 db test `employee cannot reopen closed order`.
3. **Owner types Paid = 900 with Total 800, or clears Paid to 0 after an advance:** the first is refused with `exceeds_total`; the second records a −advance entry and history shows "Paid ₹300 → ₹0". → Task 1 db tests.
4. **The browser blocks the pre-opened window at Create:** the order is still created, and the board banner shows a WhatsApp icon so the message can still be sent. → Task 6 step.
5. **Searching a slip number that was Rejected:** the order shows in results with a red "Rejected" lozenge. It never appears in a board column. → Task 2 `boardColumns` unit test.

### Task 1: Migration — Unstarted stage, no on_hold, `set_status`, `set_paid`

**Files:**
- Create: `supabase/migrations/20261120000001_jira_status.sql`, `tests/db/status.test.ts`
- Modify: the tests in `tests/db/*.test.ts` that assume 4 stages, a first stage of `Cutting`, or `on_hold`; `tests/db/fixtures.ts` if needed; `src/lib/database.types.ts` (regenerate)

**Interfaces:**
- Consumes: `_order_for_write(p_order_id, p_owner_only)` and `_log_event(o, action, from, to)` from `20261119000002_orders_rpc.sql`; the `payments` table.
- Produces the following schema changes:
  - Every existing shop gains a stage `Unstarted` at position 1, and its other stages shift up by one. Do this in two updates to avoid `unique(shop_id, position)`: first `+100`, then `-99`.
  - `admin_create_shop` (replaced, same signature and grants) seeds `Unstarted, Cutting, Stitching, Ironing, Ready`.
  - Orders with `special_state = 'on_hold'` are set to null, with a `special_state` event (`from 'on_hold'`, `to null`, actor null). Then the check becomes `in ('cancelled','delivered')`.
  - `set_special_state` is replaced so it no longer accepts `on_hold`.
  - `update orders set tracking_enabled = true`.
  - `create_order` already places new orders in the lowest-position stage, which is now Unstarted. Verify this; don't change it unless needed.
- Produces `set_status(p_order_id uuid, p_target text) returns void`, where `p_target` is a stage uuid as text, `'delivered'` or `'cancelled'`:
  - Owner: any target. Employee: stage targets only (`'delivered'`/`'cancelled'` → `not_owner`), under the `_order_for_write` assignee rule, and never on a closed order (`order_closed`).
  - Owner, stage target on a closed order: set `special_state = null` (`special_state` event to null), then set the stage (`stage` event, from/to stage ids) if it differs.
  - Stage target on an open order: same as `move_order` (`stage` event). A target equal to the current stage is a no-op with no event.
  - `'delivered'`/`'cancelled'`: set `special_state` (`special_state` event from old to new). A no-op if unchanged.
  - Errors: unknown target or a stage from another shop → `invalid_input`.
- Produces `set_paid(p_order_id uuid, p_paid int) returns void`. Owner only. Its rules:
  - `p_paid < 0` → `invalid_input`.
  - `delta = p_paid − sum(payments)`. If `delta = 0`, it's a no-op.
  - When `total_amount` is not null and `p_paid > total_amount` → `exceeds_total`.
  - It inserts one payment (`amount = delta`, `method = 'other'`, `note = 'Paid ₹<old> → ₹<new>'`) and logs event action **`'paid'`** with `from = old sum`, `to = new sum`.
- `move_order` and `add_payment` stay, because v1 tests and fixtures use them. The UI stops calling them.
