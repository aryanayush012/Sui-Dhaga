# Sui-Dhaga v1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the pre-pilot version of Sui-Dhaga, a mobile-first PWA where a tailor shop tracks every order on a stage board, with a rack location, employee assignment, payments, a public tracking link and one-tap WhatsApp messages. This covers delivery steps 1–3 of the spec.

**Architecture:** Next.js (App Router) for the screens, talking directly to Supabase from the browser. Every write goes through Postgres functions (RPCs) that check permissions and append to `order_events`. Every read of orders goes through one view, `board_orders`, which hides the customer mobile from employees. Row-level security (RLS) on every table keeps each shop's data separate. Live updates come from Realtime on `order_events`: a new event tells the board to refetch. Next.js server code is used only for the public tracking page and for actions that create logins (these need the service-role key).

**Tech Stack:** Next.js 15, React 19, TypeScript, Tailwind CSS 4, @supabase/supabase-js 2 + @supabase/ssr, Supabase CLI (local Postgres/Auth/Storage/Realtime, needs Docker), Vitest, Playwright, tsx (scripts).

**Spec:** `docs/superpowers/specs/2026-11-19-sui-dhaga-design.md`

## Global Constraints

- Node ≥ 20. npm. Source in `src/`. Path alias `@/*` → `src/*`.
- Every shop-owned table has `shop_id uuid not null references shops`. RLS is enabled on every table, with no exceptions.
- Logged-in users have no direct `insert/update/delete` grants on business tables. All mutations go through `security definer` RPCs with `set search_path = public`.
- Money is **whole rupees** stored as `integer` (no paise). *(Implementation call.)*
- Mobile numbers are stored as exactly 10 digits matching `^[6-9][0-9]{9}$`. The auth email for a user is `<mobile>@users.suidhaga.app`.
- Owner password is at least 6 characters. Employee PIN is **6 digits**, because Supabase's minimum password length is 6. *(Implementation call.)*
- "Today" for deadlines is the calendar date in `Asia/Kolkata`.
- Deadline chip: due in >2 days → none. Due in 1–2 days → `approaching` (amber). Due today → `at_risk` (orange). Past due → `overdue` (red). There is no chip when the order is in the last (Ready) stage, or is delivered or cancelled. On-hold orders still get chips.
- Seeded stages, in order: `Cutting`, `Stitching`, `Ironing`, `Ready`. The stage with the highest `position` is the Ready stage.
- Special states are `on_hold`, `cancelled` and `delivered`, kept in `orders.special_state` (null = normal).
- Tracking token: 24 random bytes (192 bits), URL-safe base64.
- Photos: compressed in the browser to a longest side of ≤ 1280 px, JPEG quality 0.7, stored in the private bucket `photos` at `<shop_id>/<uuid>.jpg`.
- UI: Hindi + English, every touch target ≥ 44 px, works at 360 px width.
- RPC errors are raised as `raise exception '<code>'`. Codes used in this plan: `not_member`, `not_owner`, `forbidden`, `invalid_mobile`, `invalid_input`, `exceeds_total`, `below_paid`, `negative_balance`, `note_required`, `not_found`, `order_closed`.

## Review Focus

1. **Mobile number formats typed at the counter** (`+91 98765 43210`, `098765-43210`, `9876543210 `) should all be accepted as the same number. A 9-digit number or one starting with 1–5 should be rejected with a clear message. → test in Task 1 (`normalizeMobile`).
2. **Two phones creating orders at the same moment** must never get the same slip number. → Task 3, `concurrent creates get distinct slip numbers`.
3. **A deactivated employee whose phone is still logged in** must not be able to read the board or move anything. → Task 2, `inactive member sees nothing`.
4. **An order moved back out of Ready and then into Ready again** (karigar mistake) should lose its "Status communicated" ✓ until the Ready message is sent again. → Task 5, `re-entering ready resets communicated`.
5. **An order due "today" checked late at night**: at 23:30 IST on 21 Nov, an order due 21 Nov is `at_risk`, not `overdue`, even though UTC is already 22 Nov on some setups. → Task 6, `uses IST date near midnight`.

- Produces in `src/lib/garments.ts`: `GARMENT_TYPES: GarmentType[]` and `GARMENT_FIELDS: Record<GarmentType, string[]>`, with field keys copied from the spec (`waist`, `hip`, `length`, `thigh`, `knee`, `bottom`, `crotch`, …). `other` has `[]`.
- Produces these RPCs. All of them write an `order_events` row (`action` in parentheses), bump `updated_at`, and raise `not_member` if there's no active member:
  - `create_order(p jsonb) returns jsonb` (`created`). Owner only. Returns `{id, slip_no, tracking_token}`. Its rules:
    - The mobile must match the regex (`invalid_mobile`).
    - It needs a name, a due date and at least 1 garment (`invalid_input`).
    - The slip number comes from `update shops set slip_counter = slip_counter + 1 … returning`.
    - The order is placed in the first stage.
    - The token is `translate(encode(gen_random_bytes(24),'base64'),'+/','-_')`.
    - If `advance` is given, it inserts the payment (`payment` event). The advance must not exceed the total when a total is set (`exceeds_total`).
    - The assignee must be an active member of the same shop (`invalid_input`).
  - `move_order(p_order_id uuid, p_stage_id uuid)` (`stage`, from/to = stage ids):
    - The owner can move any order.
    - An employee can move an order only when `assignee_id = auth.uid()` or `assignee_id is null`; otherwise `forbidden`.
    - `order_closed` if `special_state` is not null.
    - The stage must belong to the same shop.
  - `set_rack(p_order_id, p_rack text)` (`rack`). Same permission rule as `move_order`. Blank or whitespace becomes null.
  - `assign_order(p_order_id, p_member_id uuid null)` (`assignee`). Owner only.
  - `change_due_date(p_order_id, p_due date)` (`due_date`). Owner only.
  - `set_special_state(p_order_id, p_state text null)` (`special_state`). Owner only. `null` means resume.
  - `update_order_info(p_order_id, p_name text, p_mobile text, p_notes text)` (`info`). Owner only.
  - `save_garment(p_order_id, p jsonb) returns uuid` and `delete_garment(p_garment_id)` (`garment`). Owner only. An order cannot end up with 0 garments (`invalid_input`).
  - `board_orders` view. It is a definer view filtered by `shop_id = current_shop_id()` and granted to `authenticated` only. It has the `BoardOrder` columns:
    - `customer_mobile` and `tracking_token` are null unless `is_owner()`.
    - `garment_summary` is like `'2 pant, 1 shirt'`, ordered by type.
    - In this task, `comm_kind`/`communicated` are placeholder columns (`null::text`, `false`); Task 5 fills them in.
    - `paid_amount` is `coalesce(sum(payments.amount), 0)`.

### Task 4: Payments

**Files:**
- Create: `supabase/migrations/20261119000003_payments_rpc.sql`
- Test: `tests/db/payments.test.ts`

**Interfaces:**
- Produces `add_payment(p_order_id uuid, p_amount int, p_method text, p_note text) returns uuid` (`payment` event). Owner only. Its rules:
  - `amount = 0` → `invalid_input`.
  - A negative amount with a blank note → `note_required`.
  - A sum of payments above the total, when a total is set → `exceeds_total`.
  - A sum of payments below 0 → `negative_balance`.
  - Payments are allowed on cancelled orders, so refunds can be recorded.
- Produces `set_total(p_order_id, p_total int null)` (`total` event, from/to = old/new). Owner only. A total below the current paid sum → `below_paid`.
- The `payments` table has no update or delete grant for anyone except `postgres`.
